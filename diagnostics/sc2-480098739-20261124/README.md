Sol 两次原生报告时间分别早于首次连接失败 4.662 秒和 3.038 秒。报告时间不等于引擎内部首次异常指令的精确时刻。原生报告均为 Unknown System Error 480098739，ErrorType=NON-FATAL、GetLastError=0，并含 SinceLaunchEvent / CurrentGameEvent 的 Mismatch in texture reduction DB。

burnysc2 7.3.0 的 run_game 用 gather(return_exceptions=True) 收集 host/join 返回，再断言各项为 Result；异常返回可触发 main.py:529。故该断言属于后果而非已证实首因。清理引起另一连接关闭也不是第二次独立原生崩溃。真正进程退出时刻仍需进程监督日志确认。

### 入组及通过标准

- 同一请求种子不能代替真实出生检查。标准 CreateGame 没有直接指定出生坐标的字段；记录实际请求 protobuf、ResponseJoinGame.player_id、首次观测中各自主基地中心、录像 loop 0 的基地归属及坐标。
- 出生点/角色映射不匹配的启动尝试单列，不计入有效对照样本。矩阵指 2–4 场有效对照，不保证随机出生只需 2–4 次启动。
- 目标：双方正常运营，通过 loop 7169（已知最晚故障边界），继续到 loop >=10752（Faster 8:00），双方仍可响应、没有 480098739、无非计划退出，并正常保存录像与退出。
- 若提前自然完赛，保留自然终局，未覆盖时间区间不算已通过；若 Bot 停止正常建造生产，也不能将其作为同条件通过。
- 若复现，记录首个原生异常的进程/端口/角色，保留全部资料，不按比分转为比赛胜负。

暂不优先切 realtime=true：会同时改变 Step/Observation 时序、请求速率和资源调度。若新日志显示请求堆积，再做保持 game_step 与决策规则不变、只增加墙钟节奏限制的成对实验。通过仅支持速率/调度/资源压力相关，而非直接证明某种 Query 是根因。

可选零 Bot 诊断：用户另行安排重放崩溃录像；若重现，说明实时 Bot 查询不是该复现的必要条件；若播放到部分录像 EOF 不崩，不能排除未记录的最后请求或局内双客户端条件。没有在本轮启动 SC2 或执行这些实验。

## 5. 下轮最小日志规范

两端同时记录，成功局亦记录。用同一 run_id 关联每份数据。建议输出：

| 文件/层级 | 必需字段 |
| --- | --- |
| manifest.json | run_id、双方完整提交/工作树文件哈希、SC2/SDK/Python 版本、地图哈希、原始启动参数、realtime/game_step、时间上限、配置 seed、实际 RequestCreateGame.seed、录像随机字段 |
| clients.json | 每端 OS PID、API 端口、启动时间、create/join 角色、player_id、Bot 名称、窗口、实际起始基地坐标 |
| api-p1.jsonl / api-p2.jsonl | 每次发送/响应的 UTC 与单调时间、请求序号、类型、最近一次 observation loop、请求与响应长度、状态/错误；Query 各类条目数与延迟、Action 去重前后计数；崩溃前至少 20–30 秒完整 Query/Action 参数（ability、unit tag、目标、queue 等）、未响应请求 |
| native/ | 两端完整原生日志（包括正常局同通道日志）、错误报告、可用 dump；分别保存日志事件时间与采集时间、首次 480098739 和纹理事件时间/次数/归属 |
| lifecycle.jsonl | 连接/断开时间、close code/reason、所属 PID/端口、首次 SDK 异常、退出/强杀请求、实际进程退出时间和退出码 |
| resources.jsonl | 约每秒一次进程内存、系统可用提交、GPU 显存实际使用/预算、窗口/镜头状态及镜头请求计数 |
| replay/ | 原始 SC2Replay、是否部分录像/原生崩溃快照、header 末尾 loop、game/tracker 最后事件、玩家与出生映射；保留原始文件哈希 |

Observation 不必完整倾倒；保留 game_loop、status、action_errors 及对应请求序号。诊断数据应记录于公共运行器/协议边界而非参赛 Bot 战术层，控制额外 I/O 和采样干扰；完整 Query/Action 使用环形记录，异常或正常结束时归档。先保全首错进程和诊断材料，再在合理超时内清理另一端，不把 cleanup 杀进程当独立崩溃。

建议 API 事件格式（示例，仅为字段设计，不是实测）：

```json
{"run_id":"T1-example","client":"P1","pid":1234,"port":5000,"role":"create","player_id":1,"seq":42,"event":"send","type":"query","utc":"2026-11-24T06:00:00.000Z","mono_ns":1000000000,"last_obs_loop":3200,"pathing_count":2,"placement_count":12,"abilities_count":0,"request_bytes":240}
```

关键对齐要求：

1. UTC（带时区原始时间可同时保存）+ 单调时钟；启动、首次观测和每次 Step/Observation 的 loop 建立时间锚点。加速倍速不恒定，不用平均倍速反推最后请求。
2. 将最后成功 Observation、最后成功响应、最后发送但未响应请求、最后完整命令、最后目标更新、最后 tracker 事件、录像 header 末尾、原生报告 GameLoop 分开记录。最近观测 loop 只是上一次已知值，不冒充请求真正执行 loop。
3. 原生首次事件、原生报告生成、首次 WS 断开、清理请求、第二连接断开、实际进程退出、SDK 最终断言依次对齐。正常结果/保存录像后发生的连接关闭归入清理阶段。
4. 纹理事件仅在成功/失败采用相同日志通道且覆盖相同时间段时比较；不能获取内部字段时标记 unobservable/UNKNOWN，而非 false。保存首次时间、出现次数、启动期/局内及所属进程。
5. 区分请求 envelope 批数、实际条目数、字节量、每 game loop 与每现实秒速率；按客户端与类型分别统计，附最后 1/5/30 秒窗口与未完成请求。失败后不盲目重试同一连接。
