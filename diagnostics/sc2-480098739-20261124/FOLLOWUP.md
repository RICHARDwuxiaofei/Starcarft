# SC2 收尾修复与原生闪退补充调查

## 游戏时间到时

2026-11-24 的附属建筑隔离局，DeepSeek（P1）的观测推进到循环 10752，随后收到触发 SDK 游戏时间上限的观测。混元（P2）在循环 10750 发出的 4 帧 Step，直到 P1 离开后才返回。旧对局程序在 P1 的到时回调里等待 P2 的结果回调，造成约 10 秒等待超时。P2 后续得到的 Victory 是 P1 离开后的回调。该局无有效赛果，原始记录保留。

本分支带上独立的 Windows 对局程序 `bots/codex/smoke/local_arena_series.py`。在 burnysc2 7.3.0 的人工到时 Tie 没有伴随客户端权威游戏结果时，先到上限的一侧会先尝试保存截止录像，然后直接返回 SDK 收尾流程。另一侧无需越过上限或先进入结果回调。到时归类为 `game_time_limit`，断线优先保留首错。这两种情况的回调进入 `reported_result`，不会作为正式胜负或 Elo 输入。截止回放作为部分录像，离线评分只展示末尾状态。

Python 3.12.14 与 burnysc2 7.3.0 已跑 6 项离线回归，覆盖非对称步长造成的一侧阻塞、另一侧已等在回调、自然结束、先断线后到时、录像写入失败以及结果和录像输出。复跑命令为 `python -m unittest discover -s bots/codex/smoke -p test_local_arena_series.py`。本次修复没有用实战验收，也未部署到台式机。运行脚本时从仓库根目录执行，参赛位置可用 `SC2_MIZUKI_ROOT`、`SC2_WEBGPT_ROOT` 覆盖，评分环境须能导入对应录像构建的解析依赖。

## 原生错误 480098739

- 单客户端分别播放 Sol 与混元的部分录像，均到达录像末帧（循环 6689、4850），未触发同一原生错误。回放不包含两客户端在线交互。
- DeepSeek `2858976` 对混元 `f98f317` 的三场诊断各只启动一次。限速场和仅拦截混元兵营科技实验室的场次，在循环 3165 和 4773 复现原生错误；二者最后一条未获响应的混元请求分别为 421（兵营科技实验室）和 454（重工厂科技实验室）。两份原生报告均包含 `Mismatch in texture reduction DB`。
- 协议记录显示，前一场混元对同一兵营发送了 219 次同种指令，包含 19 次成功响应；后一场对同一重工厂发送了 33 次同种指令，包含 32 次成功响应。成功响应说明协议层返回 Success，不能单凭该值断言建造完成。
- 全量拦截混元附属建筑的场次未重现原生错误，双方跑到最后共有样本 7:59.91，随后遇到上面的 SDK 收尾问题。同一场 DeepSeek 对同一座建筑发出 907 次星港反应堆指令，907 次得到 Success。重复请求密度本身不足以解释闪退。三个诊断局的实际出生点不同，拦截范围与速度也不同，不能作单因素定因。

下一次由用户安排实战时，优先在正常允许附属建筑的情况下检验收尾修复。若要继续隔离原生问题，可在单独的非计分局仅对同一建筑、同一附件指令消重，保留首发和有界重试，再用未改流量的对照核验。按实际发生的出生位置记录，不退出重抽。除请求和响应外记录第一个原生失败进程的角色、PID 和游戏循环。当前未验证渲染资源、席位或附件请求状态是根因；本分支未把诊断拦截带入比赛程序。
